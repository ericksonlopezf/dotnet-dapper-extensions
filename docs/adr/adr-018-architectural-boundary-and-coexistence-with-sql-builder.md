# ADR-018: Ecosystem Demarcation — EricksonLopez.DapperExtensions vs EricksonLopez.SqlBuilder Boundary

## Status
Accepted

## Date
2026-09-04

## Context

Across the EricksonLopez data access layer, two major packages operate at Tier 2:
1. `EricksonLopez.DapperExtensions` — Established under the philosophy *"Raw SQL, Managed Infrastructure"*.
2. `EricksonLopez.SqlBuilder` — Established as an immutable AST SQL compiler, query constructor, and dialect syntax generator.

Historically, functional boundary leakage occurred when dialect execution adapters and bulk parameters (`BulkParameters`, `PostgreSqlDapperExtensions`, `TransactionExtensions`) were added to `dotnet-sql-builder`. Simultaneously, legacy migration notes in `dotnet-sql-builder` claimed that Dapper extensions had been deprecated into `SqlBuilder`.

An exhaustive architectural audit of enterprise consumers (`OpusHydra` with 34 Bounded Contexts, `JeiyelFE26` DGII e-CF Fiscal Core) established that:
- Both flagship consumers standardize 100% on `EricksonLopez.DapperExtensions` for their runtime persistence infrastructure: `IUnitOfWork`, `ISavepoint`, PostgreSQL typed array `UNNEST`, and reactive `IAsyncEnumerable<T>` streaming.
- Neither consumer references `EricksonLopez.SqlBuilder` directly.
- The fundamental principle **"ONE CAPABILITY → ONE OWNER"** requires explicit formalization of the boundary between query compilation and data access runtime.

## Decision

We formally declare the permanent architectural boundary between `EricksonLopez.DapperExtensions` and `EricksonLopez.SqlBuilder`:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        ONE CAPABILITY → ONE OWNER                      │
├───────────────────────────────────┬────────────────────────────────────┤
│ Capability Domain                 │ Authoritative Owner                │
├───────────────────────────────────┼────────────────────────────────────┤
│ SQL Query Building & Compilation  │ EricksonLopez.SqlBuilder           │
│ Dialect Syntax & AST Visitors     │ EricksonLopez.SqlBuilder           │
│ SQL Injection Roslyn Analyzers    │ EricksonLopez.SqlBuilder           │
├───────────────────────────────────┼────────────────────────────────────┤
│ [SqlEntity] DataReader Hydration  │ EricksonLopez.DapperExtensions     │
│ Unit of Work & Savepoints         │ EricksonLopez.DapperExtensions     │
│ Protocol Bulk Operations (UNNEST) │ EricksonLopez.DapperExtensions     │
│ Multi-Map Relational Hydration    │ EricksonLopez.DapperExtensions     │
│ Reactive Async Streaming          │ EricksonLopez.DapperExtensions     │
│ Connection Health & Observability │ EricksonLopez.DapperExtensions     │
└───────────────────────────────────┴────────────────────────────────────┘
```

### 1. `EricksonLopez.DapperExtensions` is the Canonical Runtime Owner
- `DapperExtensions` owns execution over `IDbConnection` and `IDbTransaction`.
- It manages transactional integrity (`IUnitOfWork`, `ISavepoint`, `ExecuteInSavepointWithRetryAsync`).
- It manages high-throughput bulk ingestion (`EricksonLopez.DapperExtensions.PostgreSql.Bulk` with `UNNEST`, `SqlBulkCopy`, `INSERT ALL`).
- It manages Native AOT multi-mapping (`MultiMapBuilder`, `[SqlEntity]` Roslyn Source Generator, `IDataReaderMapper<T>`).
- It manages unbuffered reactive streaming (`IAsyncEnumerable<T>`).

### 2. `EricksonLopez.SqlBuilder` is the Canonical Query Compiler Owner
- `SqlBuilder` compiles strongly typed lambda expressions and immutable ASTs into `(string Sql, object Parameters)`.
- It is NOT an execution framework and MUST NOT duplicate transaction management or dialect bulk insertion engines.
- `EricksonLopez.DapperExtensions` already references `EricksonLopez.SqlBuilder.Abstractions`, allowing queries generated by `SqlBuilder` to be seamlessly executed within `DapperExtensions`'s managed runtime.

## Consequences

### Positive
- Eradicates confusion across all repositories regarding where `UNNEST` and `IUnitOfWork` reside.
- Prevents redundant development across both packages.
- Preserves Native AOT compliance by ensuring `DapperExtensions` handles hydration while `SqlBuilder` handles AST rendering.

### Negative
- Developers composing dynamic SQL and requiring managed transaction boundaries reference both packages, which reflects standard clean architectural composition.
